# 0004 — 쓰기 API는 계정 없이 정적 API 키로만 최소 보호한다

## 상태
채택

## 맥락

[[0003-mvp-scope-and-user-model]]에서 "계정 없는 1인 모델"로 확정했지만, 이것이 "쓰기 API를 완전히 무방비로 공개 배포한다"는 뜻은 아니다. `PUT /api/settings`(관심 키워드·수신 시간 변경)와 `POST /api/scheduler/trigger`(수동 실행)는 공개 인터넷에 배포되는 Oracle Cloud 엔드포인트다. 인증 없이 열어두면 누구든 URL을 알아내 설정을 초기화하거나 수동 트리거를 반복 호출해 Gemini 무료 할당량(일 1,500회)을 소진시킬 수 있다.

## 결정

`PUT /api/settings`, `POST /api/scheduler/trigger` 두 쓰기 엔드포인트에 **정적 API 키**(`X-API-Key` 헤더, 서버 `SETTINGS_API_KEY` 환경변수와 비교)를 요구한다. 읽기 엔드포인트(`GET /api/briefings/*`, `GET /api/audit-logs`, `GET /api/settings`)는 그대로 공개한다.

## 근거

- 대상 위협은 "악의적 침입자로부터의 데이터 보호"가 아니라 "무작위 크롤러·봇의 남용 방지"다 — 이 프로젝트에 로그인 계정이 있는 사용자가 없으므로 진짜 인증은애초에 설계 범위 밖([[0003-mvp-scope-and-user-model]] Out of Scope).
- 정적 키는 Web 프론트엔드 번들에 그대로 노출되므로 **진짜 비밀이 아니다.** 그럼에도 이 키가 있으면, URL만 우연히 발견한 자동화 스크립트가 무심코 남용하는 흔한 경로(스캐너가 열린 REST API에 무작위 PUT을 시도하는 등)는 대부분 걸러진다.
- 읽기는 그대로 공개한다 — 금융 뉴스·환율은 애초에 공개 정보이고, 굳이 숨길 이유가 없다. 감사로그 조회도 읽기이므로 공개하되, `response_summary`에 시크릿이 섞여 들어가지 않는지는 Do 단계에서 확인하기로 함([[../../docs/02-design/features/firewatch.design]] §7 마지막 체크리스트).

## 결과·트레이드오프

**얻는 것** — OAuth/세션 같은 무거운 인증 인프라 없이, 하루 만에 구현 가능한 최소 방어선으로 가장 뻔한 남용(설정 초기화, 할당량 소진)을 막는다.

**감수하는 것** — 이 키를 아는 사람(예: 브라우저 개발자도구를 여는 누구나)은 여전히 설정을 바꿀 수 있다. **실질적 보안이 아니라 편의적 방어선**임을 명시한다. 진짜 여러 사용자가 생기면 이 방식 전체를 버리고 실제 인증으로 교체해야 한다.

## 재검토 트리거

- 다중 사용자·로그인이 필요해질 때 → 정적 키를 폐기하고 실제 인증(JWT/세션)으로 교체.
- 정적 키가 실제로 유출·남용된 사례가 생기면 → Rate Limiting 등 추가 방어선 검토.
