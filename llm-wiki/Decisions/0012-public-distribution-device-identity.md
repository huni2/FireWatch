# 0012 — 공개 배포 전환: 기기별 익명 저장을 기본으로, Google 계정 연동은 선택으로

## 상태
채택 — [[0003-mvp-scope-and-user-model]](계정 없는 1인 모델)과 [[0004-write-api-protection]](정적 API 키)을 부분 대체.

## 맥락

Play 스토어 출시 체크리스트를 진행하던 중, `UserSettings`가 여전히 [[0003-mvp-scope-and-user-model]]이 확정한 "싱글톤(id=1 고정)" 구조라는 걸 재확인했다. 개인용 도구일 때는 문제없었지만, 사용자가 "불특정 다수에게 공개 배포"를 원한다고 명확히 하면서 이 구조 자체가 블로커가 됐다 — 낯선 설치자가 설정을 바꾸면 소유자 계정도 함께 바뀌고, 모든 설치자의 기기가 같은 FCM 토큰 목록에 쌓여 전원이 같은 알림을 받는 구조였다.

또한 [[0004-write-api-protection]]이 이미 "다중 사용자·로그인이 필요해질 때 정적 키를 폐기하고 실제 인증으로 교체"를 재검토 트리거로 명시해뒀던 시점이 이번에 왔다.

기기 간 동기화 방식을 두고 사용자와 조율 — 처음엔 "기기별 익명 ID"만 제안했으나, 사용자가 "즐겨찾기한 주식을 유지하려면 실제 이메일 계정이 있어야 하지 않냐"고 지적해 계정 개념이 필요함을 확인. 이어서 "Play 스토어면 구글 자동로그인 아니냐"는 반응으로 Google Sign-In 채택. 마지막으로 "기기별로 저장되게 하고 연동은 선택으로 해도 됨"이라는 절충안으로 최종 확정 — 로그인 없이 바로 쓸 수 있는 기존 경험을 유지하면서, 원할 때만 계정을 연동해 기기 간 동기화를 얻는 구조.

## 결정

- **기본**: 기기 최초 실행 시 로컬에서 생성한 익명 `deviceId`로 식별. `GET`/`PUT /api/settings` 둘 다 `X-Device-Id` 헤더 필수.
- **선택**: `POST /api/auth/google/link`(`X-Device-Id` + Google ID 토큰)로 계정 연동. 최초로 연동하는 기기의 기존 설정(관심 종목 등)을 그대로 그 계정의 공유 행으로 승격 — "연동하면 지금까지 쓰던 게 사라진다"는 걱정을 없앤다. 이미 다른 기기가 먼저 연동해뒀으면 그 공유 행에 합류(이 기기의 기존 데이터는 버림 — 동기화가 목적이므로 의도된 동작).
- ID 토큰 검증은 직접 구현하지 않고 Google 공식 `GoogleIdTokenVerifier`(`com.google.api-client`)에 위임 — 서명·만료·audience 검증, JWKS 캐싱·로테이션을 통째로 맡긴다.
- 세션/토큰 발급이 없다 — 연동은 `device_links` 테이블에 한 번 기록되는 걸로 끝나고, 이후 요청은 계속 `X-Device-Id`만으로 식별한다(로그인 상태를 유지할 서버 세션이 없음).
- `PUT /api/settings`의 쓰기 권한이 [[0004-write-api-protection]]의 공유 `SETTINGS_API_KEY`에서 "이 `deviceId`를 안다"는 사실 자체로 바뀌었다 — 기기마다 다른 값이라 클라이언트 번들에 공유 비밀을 박아둘 필요가 없다. `SETTINGS_API_KEY`는 스케줄러 관리 엔드포인트(`/api/scheduler/*`) 전용으로 범위가 좁혀졌다.
- 스케줄러/푸시를 "생성"(전역, 하루 1회, `SchedulerJob`)과 "발송"(사용자별 `pushTime`, `PushService.notifyDueUsers`)으로 분리 — 여러 사용자가 서로 다른 `pushTime`을 가질 수 있어졌기 때문.

## 근거

- **왜 익명 기기 ID를 기본으로 하는가** — 로그인 화면·비밀번호 없이 즉시 쓸 수 있는 기존 UX를 유지. 이 앱은 결제·민감정보가 없어 "설치 즉시 사용"이 계정 생성 강제보다 우선순위가 높다.
- **왜 자체 이메일+비밀번호가 아니라 Google Sign-In인가** — 비밀번호 해싱·비밀번호 찾기용 이메일 발송 인프라를 직접 구축할 필요가 없고, Android 앱(Play 스토어 배포)과 궁합이 좋다. `$0` 예산 원칙과도 맞음.
- **왜 세션 토큰을 발급하지 않는가** — Google Sign-In을 "로그인 세션 유지 수단"이 아니라 "기기-계정 연동을 증명하는 1회성 의식"으로만 쓴다. 연동 이후엔 `device_links`가 매핑을 영구 기억하므로, 매 요청마다 ID 토큰을 갱신·재검증할 필요가 없다 — OAuth 리프레시 토큰 흐름 자체가 불필요해짐(이 프로젝트 규모에 과한 복잡도였을 것).
- **왜 `id`에 DB auto-increment(IDENTITY/SERIAL)를 안 쓰는가** — 기존 프로덕션에 이미 `id=1`(소유자, 수동 PK)이 있어 지금 와서 시퀀스로 바꾸려면 위험한 `ALTER COLUMN ... ADD GENERATED`가 필요하다. 대신 신규 행은 애플리케이션에서 생성한 랜덤 `Long`을 쓴다(63비트 공간, 이 프로젝트 규모에서 충돌 위험 무시 가능) — 스키마 마이그레이션 위험을 회피.

## 결과·트레이드오프

**얻는 것** — 공개 배포가 가능해짐(설치자 간 데이터 격리), 기존 UX(로그인 없이 즉시 사용) 유지, [[0004-write-api-protection]]이 안고 있던 "클라이언트 번들에 공유 비밀 노출" 문제가 구조적으로 해소됨.

**감수하는 것**
- 계정을 연동하지 않고 앱을 지우거나 기기를 바꾸면 설정이 사라진다(익명 모드의 태생적 한계) — 연동이 "선택"인 이유이자 대가.
- 두 번째 이후 기기가 연동하면 그 기기의 기존 데이터는 버려진다(계정의 공유 데이터로 대체) — 데이터 병합(merge)은 하지 않음, 단순함을 우선.
- `user_settings.id`가 더 이상 DB auto-increment가 아니라 애플리케이션 랜덤 생성 — 극히 드물게 충돌 가능성이 이론상 존재(재시도 로직 없음, 현재 규모에서 과한 대비로 판단해 생략).

## 재검토 트리거

- 사용자가 계정 간 데이터 "병합"(둘 다 유지하고 합치기)을 요구하면 → `AuthService.linkGoogleAccount`의 "버림" 정책 재검토.
- 실제 사용자 수가 늘어 랜덤 ID 충돌이 실측되면(사실상 불가능한 규모지만) → `user_settings.id`를 진짜 시퀀스로 마이그레이션.
- Google 계정이 없는 사용자를 위한 대안 로그인 수요가 생기면 → 자체 이메일+비밀번호 또는 다른 OAuth 제공자 추가 검토.
