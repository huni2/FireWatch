## BE-22 사용자 제공 운영 인덱스 집계 (2026-10-09)

사용자가 Supabase 실행 결과 이미지로 다음4개 인덱스 크기를 제공했다.

| 인덱스 | bytes |
|---|---|

| idx_catalog_name | 204800 |
| idx_catalog_page_order | 139264 |

표시된 인덱스 합계는622592bytes(608KiB), 페이지 정렬 인덱스는139264bytes(136KiB)다. 운영 DB에 페이지 정렬 인덱스가 존재함을 확인했다. 생성 여부와 특정 요청에서 실제 선택되는지는 구분한다. CI의 페이지 인덱스278528bytes와 차이가 있지만 데이터 배치/DB 상태가 달라 성능 개선율이나 데이터 손실로 해석하지 않는다.

이미지는 마지막 인덱스 SELECT 결과만 포함한다. 공식 기준값/초성 누락 집계, 종류·국가별 시세, 전체 시세 건수, 전체 DB·테이블 용량은 아직 미수신이다. 운영 DB 집계 전체 완료 또는 시세 수집 정상으로 처리하지 않는다.

## 적용 판단

현재2669상품 규모에서는 운영 pg_trgm 도입을 보류한다. 긴 입력의 선택적 검색에서는 이점이 있지만 한 글자/전체 목록/깊은 페이지는 이 후보로 개선되지 않았고, 후보의 존재만으로 모든 검색이 빨라지는 것도 아니다. 기존 페이지당50건과 필터·입력 길이 제한은 유지한다. 자료 규모가 늘거나 실제 운영 검색 지연이 확인되면 동일 계획/공간 검사를 다시 대조한다.

깊은 전체 목록의 정렬/페이지 비용을 BE-22 후속 최적화 대상으로 남긴다. 이번 측정 결과로 Render·Supabase 네트워크나 실제 사용자 대기시간의 원인을 확정하지 않는다. 운영 시세가 채워진 상태의 관측과 동시 부하도 별도다.

## 재현과 범위

두 CI의 catalog-search-measurement artifact에 PostgreSQL 전체 COUNT/목록 계획과 H2 보고서를 보관했다. [push CI](https://github.com/huni2/FireWatch/actions/runs/37933247478), [PR CI](https://github.com/huni2/FireWatch/actions/runs/37933255577)에서 내려받을 수 있다. 실행 방법과 각 시간 필드 정의는 [측정 안내](usage.md)를 따른다.

두 PostgreSQL 표본의 시세 행수는0이었다. 공식 자료는 실제 회사 메타데이터지만 운영 시세 전체 JOIN 성능을 대표하지 않는다. 후보 전후 회사/시세 행과 모든 검색 결과는 동일했고 후보 인덱스는 검사 후 제거했다. 고정된 기존→후보 순서와 작은 표본 때문에 개선율을 운영 개선율로 환산하지 않는다. 운영 DB/인덱스·실제 자료·APK/EAS 빌드 변경0.
