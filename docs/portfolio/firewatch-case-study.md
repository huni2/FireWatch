# FireWatch — 개발 포트폴리오 사례

기준일: 2026-10-08 · 기능 코드: `9667eb1` · 개인 프로젝트 · 웹/백엔드 배포, Android 출시 준비 중

## 소개에 바로 쓸 수 있는 문구

### 한 문장

개인 투자 기록을 시장 뉴스·AI 분석 근거와 연결하는 웹·Android 서비스를 만들고, 무료 운영 환경에서 데이터 영속화·수집 재시도·권한 분리·거래 동시성 문제를 개선했습니다.

### 프로젝트 카드

> **FireWatch | 개인 투자 점검 서비스**  
> Kotlin·Spring Boot 백엔드, React 웹, Expo Android 앱을 구성했습니다. 보유 자산을 직접 등록해 비중과 집중도를 확인하고, 관심 기업의 가격·뉴스·저장된 추천 근거를 함께 살펴볼 수 있습니다. Render·Supabase·Cloudflare Pages로 웹과 API를 배포했으며, DB 기반 수집 작업 제어와 운영자 감사로그, 주문 중복 방지, H2/PostgreSQL 통합 검증을 구현했습니다. Android는 최신 설치 빌드 검증과 Play 출시를 준비 중입니다.

### 백엔드 지원용 핵심 항목

- 운영 데이터를 외부 PostgreSQL에 저장하고 수집 실패 시 마지막 정상 관측을 보존하는 경로를 구성했습니다.
- 수집 작업을 DB lease와 KST 날짜별 실패 한도로 제어하고, 제한된 재시도·감사 기록·운영자 장애 알림을 연결했습니다.
- 포트폴리오 버전 충돌 검사와 게임 주문 요청 ID·행 잠금으로 동시 저장/중복 주문의 일관성을 관리했습니다.
- Google ID 토큰 검증과 기기별 로그인 세션을 사용하고, 공개 클라이언트 키와 서버 운영 키를 분리했습니다.
- GitHub Actions에서 H2 테스트 외에 실제 PostgreSQL 통합 검증과 웹·모바일 정적 검사를 실행합니다.

사용자 수, 매출, 운영 응답 시간 개선율 등 측정하지 않은 성과는 포함하지 않았습니다. 기여를 설명할 때는 아래 코드·테스트·운영 기록을 함께 제시합니다.

## 제품 문제와 역할

회사 가격, 뉴스, 추천 이유가 따로 흩어져 있으면 사용자는 자신의 보유 자산과 어떤 관계인지 판단하기 어렵습니다. FireWatch는 **관심 기업 → 자료와 근거 확인 → 내 보유 비중 점검**을 중심 흐름으로 삼았습니다.

개인 프로젝트 범위는 요구사항 정리, 웹/모바일 흐름, 백엔드 도메인과 API, 배포·운영, 테스트와 문서 관리입니다. Claude Code·Codex를 개발 보조에 활용했습니다. AI 생성 코드를 모두 사람이 직접 작성한 것처럼 소개하지 않고, 제품 범위·기술 선택·검증과 수정 과정에서 내린 판단을 설명합니다.

투자 서비스의 '포트폴리오'는 보유 자산 기록입니다. 이 문서는 그 서비스를 개발한 경험을 취업·개발자 포트폴리오에 소개하기 위한 별도 문서입니다.

## 사용자 흐름

| 단계 | 제공하는 경험 | 경계 |
|---|---|---|
| 시작 | 첫 자산 등록, 저장하지 않는 분석 예시, 도움말 | 증권사 보유 내역을 자동 가져오지 않음 |
| 기업 이해 | 회사명 검색·분야별 시작 목록·가격·차트·관련 뉴스 | 시작 목록은 전 시장 커버리지가 아님 |
| 분석 확인 | 추천 이유·위험·저장 근거 기사·자료 시각 | 참고 정보이며 매수 지시·수익 보장이 아님 |
| 내 기록 점검 | 원금 비중·수집 가격 평가·분야/통화 집중·ETF 지수명 중복 | 실시간 평가나 ETF 편입 종목 전체 분석이 아님 |
| 연습 | 별도 가상게임의 매수/매도·턴 결과·선택형 순위 | 모든 게임 뉴스·가격·픽은 가상 |
| 지속 이용 | 계정 연결, 관심 설정, 공지·문의 | Android 최신 설치 빌드의 실제 동작 확인은 진행 중 |

서비스의 차별점은 거래 자체보다 **투자 자료의 근거와 개인 기록을 함께 보는 점검 경험**입니다. 아하 모멘트는 검증된 지표가 아니라 사용자 테스트로 확인할 제품 가설로 관리합니다.

## 사례 1. 데이터 유실과 수집 실패를 구분하기

### 문제와 판단

초기 운영에서 컨테이너 로컬 H2 저장소에 의존해 재기동 후 기록이 사라지는 문제가 있었습니다. 이후 '데이터가 사라져 보임'은 DB 유실, 조회 실패, 새 수집 실패, 미확인 추천 근거를 각각 구분해야 하는 문제로 확장됐습니다.

### 구현

운영 DB를 Supabase PostgreSQL로 분리했습니다. 뉴스는 링크 기반 중복 제거 후 보관하고, 금융/주식 관측은 출처와 시각을 저장합니다. 신규 수집 실패가 기존 정상 관측을 지우는 동작으로 이어지지 않도록 처리합니다.

외부 호출은 `CollectionJobRunner`에서 종류·KST 날짜에 대응하는 circuit과 개별 job으로 관리합니다. DB lease를 확보한 작업만 저장하도록 소유권을 재확인하고, 네트워크 호출 중에는 저장 트랜잭션을 유지하지 않습니다. 종류별 하루 실패 3회 한도와 재시도 간격을 적용하며 429는 중지 경로로 처리합니다.

### 검증과 한계

[수집 통합 테스트](../../backend/src/test/kotlin/com/firewatch/backend/service/CollectionJobRunnerIntegrationTest.kt)와 [기존 자료 복구 테스트](../../backend/src/test/kotlin/com/firewatch/backend/web/LegacyRecoveryIntegrationTest.kt)를 근거로 설명할 수 있습니다. 실제 외부 제공처의 현재 성공 여부는 이 테스트와 별개입니다. 최근 금융 수집 장애의 복구 확인은 남아 있습니다.

운영자 진단을 접어둔 것은 화면 노출 개선입니다. 장애를 해결했다는 성과로 표현하지 않습니다.

## 사례 2. 제한된 DB 연결 예산 안에서 운영하기

### 문제와 구현

Supabase session pooler에서 `EMAXCONNSESSION`, pool_size 15 오류가 발생했습니다. 실행 인스턴스와 배포 중 인스턴스의 연결이 겹치는 상황을 고려해 Hikari 최대 연결을 3개, 최소 유휴를 0개로 설정하고 유휴 반환 시간을 60초로 지정했습니다.

### 검증과 한계

[운영 설정](../../backend/src/main/resources/application-prod.yml)과 [출시 보강 검증 기록](../reviews/2026-10-07-release-hardening.md)에 근거가 있습니다. 모든 연결 주체를 통제하는 전역 제한은 아니므로, 다른 서비스나 인스턴스가 늘면 예산을 다시 계산해야 합니다. 대규모 트래픽 대응을 검증한 성과로 확대하지 않습니다.

## 사례 3. 동시 편집과 중복 주문의 일관성

포트폴리오는 저장 버전을 확인하고 변경 이력을 남깁니다. 오래된 버전의 저장을 거절해 다른 화면의 수정 내용을 조용히 덮어쓰지 않도록 했습니다. 프론트도 미저장 입력과 저장 후 응답을 구분합니다.

게임 거래는 요청 ID로 이미 처리한 주문을 확인하고 게임 행의 쓰기 잠금을 사용합니다. 순위 점수도 클라이언트가 보내는 숫자를 신뢰하기보다 서버 장부에서 계산합니다. 주문 초기화는 입력·미리보기만 비우며 체결 기록·보유 자산·턴은 유지합니다.

근거: [PortfolioService](../../backend/src/main/kotlin/com/firewatch/backend/service/PortfolioService.kt), [GameService](../../backend/src/main/kotlin/com/firewatch/backend/service/GameService.kt), [포트폴리오 통합 검사](../../backend/src/test/kotlin/com/firewatch/backend/web/PortfolioApiIntegrationTest.kt), [게임 서비스 검사](../../backend/src/test/kotlin/com/firewatch/backend/service/GameServiceTest.kt), [순위 통합 검사](../../backend/src/test/kotlin/com/firewatch/backend/web/GameRankingIntegrationTest.kt).

현재는 한 PostgreSQL DB의 트랜잭션과 제약에 기반한 설계입니다. 분산 트랜잭션이나 시스템 전체의 exactly-once 보장으로 표현하지 않습니다.

## 사례 4. 사용자 설정과 운영 권한 분리

웹/앱에 포함되는 설정용 키는 비밀로 간주할 수 없습니다. 감사로그·수집 진단·운영 트리거에는 별도의 서버 전용 `OPERATOR_API_KEY` 또는 검증된 운영자 계정의 로그인 세션을 요구하도록 분리했습니다.

Google ID 토큰은 서버에서 검증하며 세션과 기기를 연결합니다. 화면의 이메일 문구나 클라이언트의 운영자 표시만으로 권한을 부여하지 않습니다. 일반 화면에 수집 내부 상태가 자동으로 노출되던 흐름도 제거했습니다.

근거: [OperatorAccess](../../backend/src/main/kotlin/com/firewatch/backend/service/OperatorAccess.kt), [AuthService](../../backend/src/main/kotlin/com/firewatch/backend/service/AuthService.kt), [계정 세션 검사](../../backend/src/test/kotlin/com/firewatch/backend/web/AccountSessionIntegrationTest.kt), [수집 진단 권한 검사](../../backend/src/test/kotlin/com/firewatch/backend/web/CollectionAlertAccessIntegrationTest.kt).

운영 키 실제 값, DB 비밀번호, Firebase 서비스 계정 파일은 포트폴리오 자료와 클라이언트 빌드에 포함하지 않습니다. 전체 보안 감사나 침투 테스트 완료를 의미하지는 않습니다.

## 사례 5. 현실 데이터와 게임의 성능 경로 분리

새 게임은 시드 기반으로 가격·뉴스·지표·픽을 생성합니다. 시작·주문·다음 턴에서 실제 뉴스나 AI API를 기다리는 구조를 제거했고, 과거 턴 가격을 재현할 수 있도록 구성했습니다. 현재 게임 기업은 가상 기업 5개입니다.

그래프 생성은 각 과거 턴마다 시작점부터 가격을 재계산하던 경로를 누적 계산으로 바꿨습니다. 로컬 JVM의 13개 자산 마지막 턴 그래프 구성 배치 중앙값은 약 0.220ms에서 0.054ms로 바뀌었습니다. **그래프 생성 함수의 로컬 측정**이며 운영 API나 다음 턴 응답이 4배 빨라졌다는 뜻은 아닙니다.

5개 시드·모든 자산·모든 턴의 가격 회귀를 검사했습니다. [성능 측정 범위와 확대 설계](../product/game-universe-performance.md), [그래프 회귀 검사](../../backend/src/test/kotlin/com/firewatch/backend/service/GameSimulationHistoryTest.kt)를 함께 제시합니다. 전 종목 확대는 응답 크기·게임 버전 호환성·페이지 조회가 먼저 필요한 후속 작업입니다.

브라우저 점검에는 테스트 응답으로 구성한 화면 검증이 포함됩니다. 사용자 데이터와 실제 주문/문의/순위 등록을 운영 환경에 생성하지 않고 검사했습니다. 로컬 브라우저 검사 스크립트 일부는 저장소 밖 작업 자료이므로 README의 재현 가능한 CI 범위와 구분합니다.

## 발표·면접에서 설명할 순서

1. 시장 자료를 개인 기록과 연결하려는 제품 문제와 실제 거래를 제외한 범위.
2. 컨테이너 저장소 유실 → 외부 DB → 수집 기록/실패 처리로 발전한 이유.
3. 무한 재시도 대신 작업 소유권·한도·감사 기록을 선택한 운영 판단.
4. 버전 충돌·주문 중복·권한 경계를 실제 코드와 테스트로 설명.
5. 무료 환경의 한계와 아직 출시 전인 Android, 다음 검증 과제를 공개.

## 남은 과제

- 최신 APK 설치에서 Google 로그인, 푸시 실수신, 계정 삭제, 공지·문의·게임 동작 확인.
- 금융 데이터 수집 장애 원인 확인과 실제 정상 수집/복구 확인.
- 첫 화면의 안내 과다·정보 순서·모바일 검색 흐름·실패 상태를 포함한 UI/UX 개선.
- 투자 정보 제공 범위·개인정보 처리·Play 제출 문구의 실제 기능 일치 확인.
- 검색 카탈로그 확대, 게임 실제 기업명 도입과 버전 호환성, 데이터 보관량/비용 관리.

완료 여부는 [열린 과제](../../llm-wiki/Next-Tasks.md)와 최신 로그를 함께 확인합니다. 과거 과제의 '배포 대기' 표기가 최신 상태와 다를 경우 코드·최신 검증 기록을 우선합니다.
